# **Business Rules — Messaging Platform with Externalized Chat (Tinode)**

## **1. User Management Rules**

### **BR-U1 — Unique User Identity**
- Every user **must have a unique identifier** (`UserID`) generated by the system.
- Email addresses must be **unique**, **verified**, and **immutable after verification**.

### **BR-U2 — Authentication Requirements**
- Users must authenticate using:
  - Secure password (minimum complexity rules apply), **and**
  - Optional 2FA (email or mobile-based).
- Authentication tokens must follow **JWT** or **OAuth2** standards.

### **BR-U3 — Authorization Levels**
- The system defines the following roles:
  - **Standard User**
  - **Coach / Professional**
  - **Administrator**
- Each role must have **clearly separated access rights**.

### **BR-U4 — Account Status**
- A user can be in one of the following states:
  - **Active**
  - **Suspended**
  - **Deactivated**
- Suspended or deactivated users **cannot initiate or receive conversations**.

---

## **2. Profile & Data Privacy Rules**

### **BR-P1 — Mandatory Profile Fields**
Each user profile must contain:
- First name, Last name  
- Email  
- Country  
- Profile type (Standard / Coach)

### **BR-P2 — Personal Data Isolation**
- SQL Server stores **only business-related profile data**.
- Tinode stores **only messaging data**.
- No sensitive personal information may be duplicated in Tinode.

### **BR-P3 — GDPR Compliance**
- Users must be able to:
  - Export their personal data.
  - Request complete deletion (except legal retention obligations).
  - Withdraw consent for data processing.

---

## **3. Messaging Rules (Externalized via Tinode)**

### **BR-M1 — Conversation Creation**
- A conversation (Tinode topic) must be created when:
  - A user initiates a chat with another user.
- The application backend must ensure **both users exist** in SQL Server before asking Tinode to create the topic.

### **BR-M2 — Participant Rules**
- A conversation must include at least **two participants**.
- Only authenticated SQL users may be associated with a Tinode account.
- A user’s Tinode ID must remain linked to their SQL `UserID`.

### **BR-M3 — Message Constraints**
- Messages must follow:
  - Maximum length rules.
  - Allowed file formats.
  - Maximum attachment size.

### **BR-M4 — Message Status**
Tinode must always return:
- **Delivered**
- **Read**
- **Failed**
- **Pending**

The backend must store only **high-level status logs** (not message bodies) for legal and auditing purposes.

### **BR-M5 — Secure Storage**
- Tinode handles end-to-end encryption.
- No decrypted message content may be stored in SQL Server.

---

## **4. Integration Rules (SQL Server ⇆ .NET ⇆ Tinode)**

### **BR-I1 — Source of Truth**
- **SQL Server is the single source of truth** for:
  - User accounts  
  - Permissions  
  - Subscription plans  
- Tinode is the source of truth only for:
  - Messages  
  - Chat topics  
  - Chat metadata  

### **BR-I2 — Synchronization Logic**
- When a new user is created in SQL Server:
  - The backend must automatically create a matching Tinode account.
- When a user is deactivated:
  - Their Tinode account must be suspended.

### **BR-I3 — Cascade Rules**
Actions in SQL Server must produce these cascades:

| SQL Action | Tinode Reaction |
|-----------|------------------|
| User deleted | Delete Tinode account & revoke tokens |
| User renamed | Update Tinode profile display name |
| User blocked | Prevent messaging with blocked targets |

---

## **5. Notification Rules**

### **BR-N1 — Real-Time Delivery**
- All message events must trigger real-time push notifications:
  - Message received
  - Message read
  - User typing (optional)
- Delivery must use:
  - SignalR, or
  - Tinode real-time WebSockets

### **BR-N2 — Offline Rules**
- If a user is offline:
  - Notifications must be delivered via push (Firebase / Apple Push).
  - Messages must remain stored by Tinode until retrieved.

---

## **6. Security Rules**

### **BR-S1 — Transport Security**
- All communication must use:
  - **HTTPS**
  - **WSS (secure WebSockets)**

### **BR-S2 — Encryption**
- Tinode must enforce **end-to-end encryption**.
- SQL Server must encrypt:
  - At-rest data,
  - Sensitive fields using column encryption.

### **BR-S3 — Audit Logs**
The system must store audit logs for:
- User login attempts
- Account creation
- Suspensions
- Role updates

Message bodies must **never** appear in audit logs.

---

## **7. Billing & Subscription Rules (Optional)**

### **BR-B1 — Subscription Tiers**
Billing plans may limit:
- Message history retention
- Storage capacity
- Maximum number of contacts
- Encrypted attachment size

### **BR-B2 — Automatic Expiration**
When a subscription expires:
- User is downgraded to free tier.
- Tinode storage quotas must be adjusted automatically.

---

## **8. System Reliability Rules**

### **BR-R1 — Failed Delivery Policy**
If Tinode returns a failed delivery:
- The backend must retry according to a configurable retry policy.

### **BR-R2 — Message Integrity**
Duplicate messages must be prevented using:
- Unique client-generated message IDs
- Server-side deduplication logic

### **BR-R3 — Disaster Recovery**
Where applicable:
- SQL backups every 24h
- Tinode data snapshots every 24h
- Cold storage retention for 30 days

---

## **9. Logging & Monitoring Rules**

### **BR-L1 — Monitoring Requirements**
The system must monitor:
- Authentication failures
- Tinode connection errors
- Backend exceptions
- Latency spikes

### **BR-L2 — Centralized Logs**
Logs must be centralized using:
- ELK (ElasticSearch + Logstash + Kibana), or
- Azure Application Insights
